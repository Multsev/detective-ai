# Программа и методика испытаний Detective AI

- Версия документа: 1.0
- Дата: 2 сентября 2026 г.
- Объект испытаний: локальное веб-приложение Detective AI
Тип испытаний: ручная приёмка интерфейса + автоматическая регрессия

## 1. Назначение

Документ предназначен для последовательной проверки всех доступных пользователю экранов, кнопок, меню, сочетаний клавиш, сценариев исследования и интеграций Detective AI.

Цель испытаний — подтвердить, что:

- каждое видимое действие доступно в правильном контексте и даёт понятный результат;
- данные дела сохраняются и восстанавливаются без потерь;
- AI-исследование, вопросы, материалы и обновления образуют непрерывный сценарий;
- ошибки Codex, Google, MCP, сети и файлов не приводят к зависанию или скрытой потере результата;
- интерфейс остаётся управляемым на малом окне и при большом графе.

## 2. Объём и границы

Проверяются:

- верхнее меню, доска, карточки, связи, контекстные меню и сочетания клавиш;
- инспектор карточки и связи;
- файлы дел, материалы, заметки, реквизиты и история;
- поиск информации, поиск связи и разрешение вопросов;
- центр обновлений, очередь исследований, фильтры и легенда;
- настройки Codex CLI, доски, Google Контактов и MCP;
- адаптивность, доступность, производительность и восстановление после ошибок.

ПМИ не подтверждает истинность найденных сведений. Для AI-результата проверяются происхождение, дата, структура, дедупликация и возможность перейти к источнику. Содержательный вывод всегда проверяет человек.

## 3. Условия проведения

### 3.1. Окружение

- macOS, актуальная версия Chrome или встроенного браузера Codex;
- Node.js 22 или новее;
- приложение запущено командой `npm run dev`;
- интерфейс открыт по адресу `http://localhost:5173`;
- API доступен по адресу `http://localhost:8787`;
- для AI-сценариев установлен и авторизован Codex CLI;
- для Google-сценариев используется тестовый Google-аккаунт с People API и несколькими тестовыми контактами;
- реальные персональные данные, секреты и рабочие контакты в испытаниях не используются.

### 3.2. Разрешения экрана

Полный прогон выполняется минимум в четырёх размерах окна:

| Профиль | Размер | Назначение |
|---|---:|---|
| A | 1920×1080 | основной рабочий экран |
| B | 1440×900 | типичный ноутбук |
| C | 1280×720 | компактное окно |
| D | 800×600 | проверка переполнения и доступности действий |

Масштаб браузера для основного прогона — 100%. Отдельно выполнить проверки при 125% и 150%.

### 3.3. Набор тестовых данных

Подготовить отдельную папку без конфиденциальных данных:

- `Иван Морозов.pdf` — PDF с текстовым слоем;
- `Отчёт_№1.docx` — Word с кириллицей, таблицей и ссылкой;
- `Реквизиты.xlsx` — Excel с несколькими листами;
- `факты.md`, `заметка.txt`, `данные.csv`, `объект.json`;
- PDF-скан без текстового слоя;
- неподдерживаемые старые `sample.doc` и `sample.xls`;
- файл больше 24 МБ;
- две одинаковые копии файла с разными именами;
- изменённая редакция ранее загруженного файла;
- контакт «Иван Тестовый» с телефоном, email, компанией, должностью и заметкой;
- контакт с минимальными данными — только имя.

Создать дело с карточками всех типов: человек, компания, документ, событие, место, вопрос и заметка. Добавить не менее 12 связей разных статусов доказательности.

## 4. Правила фиксации результата

Для каждого пункта ставится один статус:

- `PASS` — фактический результат полностью совпал с ожидаемым;
- `FAIL` — найдено отклонение;
- `BLOCKED` — проверка невозможна из-за внешней зависимости;
- `N/A` — сценарий обоснованно неприменим к сборке.

При `FAIL` обязательно приложить снимок экрана, размер окна, шаг воспроизведения и запись консоли браузера, если в ней есть ошибка.

Критичность дефекта:

| Уровень | Значение |
|---|---|
| P0 | потеря/повреждение дела, утечка секрета, приложение не запускается |
| P1 | основной сценарий не выполняется, интерфейс заблокирован |
| P2 | функция работает неверно или важное действие трудно обнаружить |
| P3 | визуальное, текстовое или малозначительное отклонение |

## 7. Рекомендуемый порядок прогонов

### Дымовой прогон — 10–15 минут

`PRE-02…05`, `UI-01…07`, `CASE-01…03`, `BOARD-01…05`, `CTX-01…08`, `MAT-01…05`, `INFO-01…09`, `SET-01…06`.

Результат: можно быстро решить, пригодна ли сборка для дальнейшей проверки.

### Полный функциональный прогон — 2–3 часа

Все разделы 6.1–6.15, затем Google и MCP при доступных тестовых подключениях.

### Регрессия перед выпуском

Все автоматические проверки, весь дымовой прогон, а также `INFO-10…20`, `REL-01…10`, `Q-01…12`, `HIST-01…12`, `NF-01…12`, `A11Y-01…10`.

## 8. Критерии приёмки

Сборка допускается к использованию, если одновременно выполнены условия:

- `PRE-01…06` имеют статус `PASS`;
- нет открытых дефектов P0 и P1;
- все доступные основные сценарии `CASE`, `BOARD`, `MAT`, `INFO`, `REL`, `Q` имеют `PASS`;
- ни один успешный или пустой AI-запуск не теряется из истории;
- импорт/экспорт и перезагрузка не приводят к потере данных;
- на 1280×720 все команды доступны без выхода за экран;
- `BLOCKED` по внешней интеграции содержит причину и доказательство, а не засчитывается как успешная проверка.
